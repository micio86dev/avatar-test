# Reusable Interview Links Specification

## Purpose

A reusable interview link is ONE opaque, non-expiring, revocable URL bound to exactly one
organization and one project, for demos, trade-fair kiosks and internal testing. Every
redemption creates a fresh "visitor" participant in that project, identified by the name and
email the visitor enters, and returns the standard candidate JWT. The full URL is shown
exactly once, at creation; only a SHA-256 hash is stored. Single-use, 30-minute
`typ:sso-link` entry links are a different mechanism and do not change.

Coverage target: 95% on redemption, tenant scoping, authorization and secret handling
(security-critical); 85% overall.

This capability was promoted from the change `reusable-interview-links`. The text below is
the original specification RECONCILED with what was implemented and verified (api slices
B1a to B4, frontend B5, backoffice B6a to B6c). Where the implementation differs from the
original delta, the implementation won and the spec says so inline ("Reconciled with the
implementation") and in the closing section.

It was amended by the change `reusable-link-visitor-identity`: a visitor now ALWAYS provides
a name and an email before the interview starts, a duplicate email in the project is refused
with 409, and the retention purge redacts the email together with the name. That text is
reconciled with the implementation in the same way (api slices 1a to 5; the frontend, the
backoffice copy and the admin participants search are specified in `interview-frontend`,
`admin-backoffice` and `admin-read-api`).

---

## Non-Goals

- Any change to sso-links, `GET /api/sso/exchange`, the entry-link mint, their disclosure,
  or the `participant-sso` "No Revocation Semantics" requirement.
- Re-enabling a disabled link, editing a link, rotating a token, or showing the URL again
  (a lost link means creating a new one).
- Per-link usage caps, per-link expiry dates, scheduled activation windows (the project's
  own `goes_live_at` / `deadline_at` already bound every redemption).
- Verifying ownership of a visitor's email (one-time code or confirmation link): the identity
  is self-declared and unverified.
- Terminating visitor sessions already in progress when a link is disabled.
- A participants-list filter by link and dashboard KPI exclusion (visitors are included; see
  "Visitors Are Ordinary Participants Downstream").
- Public `/v1` exposure of the link marker; creating reusable links through M2M credentials.
- Mobile support: the candidate app's SA-11 desktop-only gate still applies.
- A per-tenant privacy-policy URL, a consent checkbox, or tenant-editable notice text: the
  visitor sees one short fixed it/en notice (see `interview-frontend`).
- G-43 (a functional `lower(email)` unique index for all enrolment paths) and normalizing the
  other enrolment paths' email handling.
- Backfilling or deleting legacy anonymous visitor rows.
- Solving proxy trust for the per-IP limiter (see "Known limitations and owner decisions").

---

## Vocabulary

- **link**: one row of `reusable_interview_links`.
- **link token**: the raw secret, shown once inside the URL fragment.
- **visitor**: the participant row created by one redemption.
- **visitor identity**: the `display_name` and `email` a visitor types before a redemption.
- **identity fields**: those two body fields of the redeem request.
- **Disable**: the only revocation verb (UI word, API word, audit word and column name).
- **redemption**: one successful call of `POST /api/reusable-links/redeem`, which requires a
  valid identity.
- **link id**: the link's public id, `rlk_` followed by a 26-character ULID. It is the only
  identifier of a link in any API payload or URL.

## Requirements

### Requirement: Reusable Link Schema And Binding

The system MUST persist links in a dedicated table `reusable_interview_links` with: an
internal id; a public id (`public_id`, a 26-character ULID rendered as `rlk_<ULID>`,
non-sequential, generated by the model on creation); `organization_id` (NOT NULL FK, removed
with its organization); `project_id` (NOT NULL FK, removed with its project); `label`
(nullable string, at most 120 characters); `lang` (NOT NULL, at most 10 characters, resolved
at creation); `token_hash` (`char(64)`, NOT NULL, UNIQUE, constrained to 64 lowercase hex
characters); `token_prefix` (NOT NULL, at most 16 characters, constrained to start with
`beai_rl_`); `uses_count` (integer, NOT NULL, default 0, constrained to be at least 0);
`last_used_at` (nullable `timestampTz`); `created_by` and `disabled_by` (nullable references
to a user, set to NULL when that user is deleted); `disabled_at` (nullable `timestampTz`);
`created_at`, `updated_at`. There MUST be NO `expires_at` column and NO `revoked_*` column.

(Reconciled with the implementation: the original delta named the disable columns
`revoked_at` and `revoked_by`. The implemented vocabulary is `disabled_at` and
`disabled_by` throughout the table, the API, the audit rows and the UI, so that one verb
names the one operation. The constraint names are explicit and pinned by tests:
`reusable_interview_links_{token_hash,token_prefix,uses_count}_check`,
`_public_id_unique`, `_token_hash_unique`, `_org_project_index`.)

`organization_id` and `project_id` MUST be set server-side from the route project resolved
under the caller's tenant; they MUST NOT be read from the request body and MUST NOT be
mass-assignable. The model's `$fillable` MUST be exactly `['label']`: `token_hash`,
`uses_count`, `last_used_at`, `disabled_at` and `disabled_by` MUST NOT be mass-assignable
either. The internal integer id MUST NOT appear in any API payload; the public id is the
only identifier.

The model MUST be a tenant-scoped model like every other organization-owned table. The one
documented exception to tenant scoping is the public redemption, which has no organization
context and looks the row up by hash; the named `tenant` global scope MUST be lifted on this
model only inside the redemption action (an architecture test pins this).

Every composite index on the table MUST lead with `organization_id` (D22): the table's own
index is `(organization_id, project_id, created_at)`. The single-column UNIQUE index on
`token_hash` is the one documented exception: the unauthenticated redemption has no
organization context and looks the row up by hash alone (the same shape as
`api_clients.key_hash`).

`participants` MUST gain a nullable column `reusable_interview_link_id` (FK to the link,
`ON DELETE SET NULL`) and a PARTIAL index `participants_org_reusable_link_index` on
`(organization_id, reusable_interview_link_id) WHERE reusable_interview_link_id IS NOT NULL`
(nearly every participant carries NULL), created without blocking writes on the hot table
(`CREATE INDEX CONCURRENTLY`, so the migration runs outside a transaction) and safe to run
twice. The FK MUST be added `NOT VALID` and then validated, so no long lock is taken on
`participants`. No existing participants constraint or index changes. The migrations
(`2026_10_01_100000` for the table and `2026_10_01_100100` for the participants column) MUST
be additive, rerunnable (a second run is a no-op and repairs an invalid index or a
`NOT VALID` constraint left by an interrupted run) and reversible (`down` of the second
removes the index, the constraint and the column, each step guarded; `down` of the first
drops the table; visitors already created survive as ordinary participants without the
marker).

(Reconciled with the implementation: the original delta described a plain index; the
participants index is partial, the same shape as the external-reference indexes, because the
marker is NULL on almost every row.)

`token_hash` MUST be excluded from the model's array/JSON serialization.

### Requirement: Token Format, Generation And Hash-Only Storage

A link token MUST be `beai_rl_` followed by `base64url(random_bytes(32))` without padding:
8 + 43 = 51 characters, carrying 256 bits from a cryptographically secure source. It is
opaque (NOT a JWT): it has nothing to decode, no `exp` and no claims. The strict format is
`^beai_rl_[A-Za-z0-9_-]{43}\z` (the end anchor is `\z`, never `$`, because `$` accepts a
trailing newline).

Only `token_hash` = lowercase hex SHA-256 of the full raw token string (marker included)
MUST be persisted. `token_prefix` MUST be the marker plus the first 8 random characters (16
characters in total); it identifies a link in lists and MUST NOT authenticate. The raw token
MUST exist only in the body of the single 201 creation response (inside the URL) and in the
URL fragment the operator copies; it MUST NOT be persisted, logged, audited, queued or
cached by the API.

Generation, hashing, prefix derivation and format validation MUST live in one generator
component (`ReusableLinkTokenGenerator`) used by creation, redemption and the redemption
limiter.

#### Scenario: Shape, length and entropy

- GIVEN 1,000 generated tokens
- WHEN each is inspected
- THEN every token matches `^beai_rl_[A-Za-z0-9_-]{43}\z`, is 51 characters long, and its
  43-character body decodes (base64url) to 32 bytes
- AND all 1,000 tokens are distinct

#### Scenario: The generator uses a secure source

- GIVEN the generator source
- WHEN it is inspected by an architecture test
- THEN it draws randomness only from `random_bytes` (no `rand`, `mt_rand`, `uniqid`,
  `Str::random`, time- or id-derived input)

#### Scenario: Only the hash is stored

- GIVEN a link was created and its raw token read from the 201 response
- WHEN every column of the row is inspected
- THEN `token_hash` equals the lowercase hex SHA-256 of the raw token and is 64 characters
- AND no column contains the raw token, and the raw token appears in no other table

#### Scenario: The prefix identifies but does not authenticate

- GIVEN a stored link with `token_prefix = "beai_rl_AbCdEfGh"`
- WHEN the prefix, or any truncation or extension of the real token, is submitted to the
  redemption endpoint
- THEN the generic 404 is returned and no participant is created

#### Scenario: Format validation rejects near misses

- GIVEN strings of 50 and 52 characters, the wrong marker (`beai_rk_`, `beai_live_`), a `+`
  or `/` or `=` in the body, surrounding whitespace and a trailing newline
- WHEN each is checked against the format
- THEN each is rejected before any database read

### Requirement: Creating A Link

`POST /api/projects/{project}/reusable-links` MUST create a link for the route project, on
the `auth:api` guard plus `TenantContext`, with the `org.context` middleware every
organization-owned write uses. `{project}` is the project's INTEGER id, exactly like the
existing `projects/{project}/questions` routes; the link is addressed everywhere else by its
`rlk_` public id.

(Reconciled with the implementation: the original delta said `{project}` was the project's
public id. The implemented admin routes use the integer id as the route parameter, the same
convention as `ProjectQuestionController`; the backoffice passes `editingProject.id`.)

The body MAY carry exactly one input: `label` (string, trimmed, at most 120 characters; an
empty or whitespace-only value is stored as NULL). The request takes NO `lang` input: any
other key in the body, including `lang`, is ignored. The link's `lang` MUST be resolved once,
at creation, from the project (`project.language`, falling back to the application's
fallback locale), and stored non-null; a later change to the project's language MUST NOT
change the link's `lang`.

(Reconciled with the implementation: the original delta accepted an optional `lang`. The
implementation resolves the language from the project only; the backoffice reusable mode
never collected one.)

Authorization MUST be `ParticipantPolicy::create` (`admin` and `operator`). The checks MUST
run in this order: (1) authorize; (2) resolve the project inside the caller's tenant (a
project of another organization or a soft-deleted project is 404); (3) validate `label`
(422 naming `label`); (4) the accessibility gate shared with the entry-link mint (project
`active`, `goes_live_at` not in the future, `deadline_at` not in the past): a project that
fails it is refused with HTTP 403 and the body `{"message": "entry_link_project_closed"}`;
(5) the interviewability predicate shared with the SSO exchange: a project that fails it is
refused with HTTP 422 and the error code `PROJECT_NOT_INTERVIEWABLE`. A refused request
stores no link.

On success the response MUST be HTTP 201 with `{"data": <link>, "entry_url": "<absolute
URL>"}`. `<link>` is the same resource a list item is (see "Listing Links Never Discloses
The Token Or Its Hash"): public id, `label`, `token_prefix`, `lang`, `status` (`active`),
`uses_count` (0), `last_used_at` (null), `created_by`, `created_at`, `disabled_at` (null).
`entry_url` is the one and only carrier of the token. The response MUST NOT contain the bare
token as a separate field, `token_hash`, or any expiry field. Each call creates a distinct
link with a distinct token (no de-duplication by label or project).

#### Scenario: Admin creates a link

- GIVEN an authenticated `admin` of organization A and an active, interviewable project P of A
- WHEN `POST /api/projects/{P}/reusable-links` is called with `{"label": "Milan fair stand"}`
- THEN HTTP 201 is returned with `data.id` starting `rlk_`, `data.label = "Milan fair stand"`,
  `data.status = "active"`, `data.uses_count = 0`, `data.last_used_at = null`, a
  16-character `data.token_prefix`, and `entry_url`
- AND exactly one row exists for P with `created_by` = the admin

#### Scenario: Operator creates a link

- GIVEN an authenticated `operator` of organization A
- WHEN the same request is made
- THEN HTTP 201 is returned

#### Scenario: The response carries the URL once and nothing else secret

- GIVEN a successful creation
- WHEN the response body is inspected
- THEN `entry_url` contains the token exactly once, after `#`
- AND there is no key named `token`, `link_token`, `token_hash`, `expires_at`, `ttl` or
  `expires_in` and no separate bare-token field

#### Scenario: Label validation

- GIVEN a label of 121 characters, then 120 characters, then `"   "`, then an array
- WHEN each is submitted
- THEN the 121-character label returns 422 naming `label` and nothing is stored
- AND the 120-character label is accepted unchanged
- AND the whitespace-only label is stored as NULL
- AND the array returns 422 naming `label`

#### Scenario: The language is resolved from the project once and stored

- GIVEN a project with `language = "en"`
- WHEN a link is created
- THEN the stored `lang` is `en`
- AND changing the project's language afterwards does not change the stored value

#### Scenario: A lang in the body is ignored

- GIVEN a creation body that also carries `lang = "it"` on a project whose language is `en`
- WHEN the request is submitted
- THEN HTTP 201 is returned and the stored `lang` is `en`

#### Scenario: The checks run in the documented order

- GIVEN a viewer, then an admin on a project of another organization, then an admin with an
  over-long label on a closed project, then an admin on a closed project, then an admin on
  an open project that is not interviewable
- WHEN each creates a link
- THEN the answers are 403 (policy), 404, 422 (`label`), 403 (`entry_link_project_closed`) and
  422 (`PROJECT_NOT_INTERVIEWABLE`) respectively, and no row is stored by any of them

#### Scenario: A project that is not accessible refuses creation

- GIVEN a project that is `draft`, or `inactive`, or has `goes_live_at` in the future, or
  `deadline_at` in the past
- WHEN a link is created for it
- THEN HTTP 403 with `{"message": "entry_link_project_closed"}` is returned and no row is

#### Scenario: Another organization's or a deleted project is not found

- GIVEN an admin of organization A and a project of organization B, or a soft-deleted
  project of A
- WHEN a link is created for it
- THEN HTTP 404 is returned and no row is stored

#### Scenario: Two creations yield two distinct links

- GIVEN two identical creation requests for the same project
- WHEN both succeed
- THEN two rows exist with different public ids, `token_hash` values and `entry_url` tokens

### Requirement: The Link URL Is Composed From The Candidate App Origin With The Token In The Fragment

`entry_url` MUST be `{CANDIDATE_APP_URL}[/{lang}]/interview/reusable#{token}`. The origin
MUST come from `config('interview.candidate_app_url')` and MUST NOT fall back to
`config('app.url')`. The locale prefix MUST follow the existing rule computed from the link's
stored `lang` by the one component that owns it (`EntryLinkUrlComposer`): `it` (the frontend
default, `prefix_except_default`) is unprefixed, every other supported locale is prefixed,
and a locale the candidate app does not support is composed unprefixed with the composer's
existing warning. The token MUST be carried in the URL fragment only, never in the path or
query, so that it is not sent to servers, proxies, access logs or `Referer`.

When `CANDIDATE_APP_URL` is unset or empty, creation MUST fail loudly (an explicit
configuration error, HTTP 500, never a 201 with a malformed URL). The URL MUST be composed
BEFORE the row is inserted, so a configuration failure leaves no stored link whose token was
never disclosed.

#### Scenario: Italian link has no locale prefix

- GIVEN `CANDIDATE_APP_URL = https://interview.example.com` and a link with `lang = "it"`
- WHEN the URL is composed
- THEN `entry_url` equals `https://interview.example.com/interview/reusable#<token>`

#### Scenario: English link carries the locale prefix

- GIVEN a link with `lang = "en"`
- WHEN the URL is composed
- THEN `entry_url` equals `https://interview.example.com/en/interview/reusable#<token>`

#### Scenario: The token is never in the path or query

- GIVEN any composed URL
- WHEN its path and query are inspected
- THEN neither contains any part of the token; the fragment is the only carrier

#### Scenario: Unset origin fails loud and stores nothing

- GIVEN `CANDIDATE_APP_URL` is unset
- WHEN a link is created
- THEN the request fails with an explicit configuration error (HTTP 500)
- AND no `entry_url` is composed from `config('app.url')`
- AND no row is stored for that request

### Requirement: Listing Links Never Discloses The Token Or Its Hash

`GET /api/projects/{project}/reusable-links` MUST return every link of that project as
`{"data": [...]}`, including disabled links. The list is not paginated (it is bounded per
project) and MUST NOT be silently truncated. The order MUST be: active links first, then
disabled links, each group newest first (`created_at` descending).

(Reconciled with the implementation: the original delta said "newest first". The
implemented order is active first, then newest, so a project's usable links are never buried
under disabled ones.)

Each item MUST carry exactly these ten keys and nothing else: `id` (the public id),
`label`, `token_prefix`, `lang`, `status` (`active` or `disabled`, derived from
`disabled_at`), `uses_count`, `last_used_at`, `created_by`, `created_at` and `disabled_at`.
`created_by` is the creator's display name only, as `{"name": <string>}`, or `null` when the
creator is unknown or was deleted; it MUST NOT carry the creator's id or any other user
attribute. An item MUST NOT carry the token, `token_hash`, `entry_url`, any URL, the internal
id, or `organization_id`, at any nesting depth. The creator MUST be loaded with the list in a
constant number of queries (no per-row query).

Authorization is `ParticipantPolicy::create`; the project is resolved inside the caller's
tenant. The list is not gated on the project's current state: links of a closed project can
still be listed and disabled.

#### Scenario: List shows metadata only

- GIVEN a project with one active link used 3 times and one disabled link
- WHEN an admin lists the project's links
- THEN HTTP 200 returns both, the active one first, with `status` `active` and `disabled`,
  `uses_count` 3 on the first
- AND no item contains the token, `token_hash`, `entry_url` or an integer `id`

#### Scenario: The key set is pinned

- GIVEN any listed link
- WHEN its keys are inspected
- THEN they are exactly the ten keys above, and `created_by` is `{name}` or `null`, so an
  added secret-bearing field fails the test

#### Scenario: Active links come first, then newest first

- GIVEN a disabled link created last, an active link created first and an active link created
  second
- WHEN the project's links are listed
- THEN the order is the active link created second, the active link created first, then the
  disabled link

#### Scenario: A link of another project or organization never appears

- GIVEN links of project P, of another project P2 in the same organization, and of
  organization B
- WHEN the links of P are listed
- THEN only P's links are returned

#### Scenario: A closed project still lists its links

- GIVEN a project that is now `inactive` or past `deadline_at`
- WHEN an admin lists its links
- THEN HTTP 200 returns them

#### Scenario: A project with no links returns an empty list

- GIVEN a project with no links
- WHEN the list is requested
- THEN HTTP 200 returns `{"data": []}`, not 404

#### Scenario: The list adds no per-row query

- GIVEN a project with 10 links created by different users
- WHEN the list is read
- THEN the number of queries does not grow with the number of links

### Requirement: Disabling A Link Is Idempotent, Immediate And Irreversible

`DELETE /api/projects/{project}/reusable-links/{link}` (the link identified by its `rlk_`
public id, the project by its integer id) MUST disable the link: set `disabled_at` to now and
`disabled_by` to the acting user, without deleting the row, and respond HTTP 204. The state
MUST be re-read under a row lock (`SELECT ... FOR UPDATE`) inside the transaction, so two
concurrent disables serialize. Disabling an already-disabled link MUST also respond 204, MUST
NOT change `disabled_at` or `disabled_by`, and MUST NOT write a second audit row. The audit
row of the first disable MUST be written AFTER the transaction commits, so a failing audit
write cannot abort the transaction that holds the user's change. Disable is not gated on the
project's state.

A link id that is malformed, does not belong to the route project, belongs to another
organization, or does not exist MUST be 404. There MUST be NO operation that re-enables,
edits, rotates or re-shows a link: the admin surface for links is exactly create, list,
disable.

A disabled link's `uses_count`, `last_used_at`, label and prefix are retained and listed.
Participants created by it are untouched.

#### Scenario: Admin disables a link

- GIVEN an active link
- WHEN an admin calls `DELETE /api/projects/{P}/reusable-links/{rlk_...}`
- THEN HTTP 204 is returned, `disabled_at` is set, `disabled_by` is the admin, and the row
  still exists
- AND the list shows `status = "disabled"` with `uses_count` unchanged

#### Scenario: Disable is immediate

- GIVEN an active link, then its disable returned 204
- WHEN its token is redeemed
- THEN the generic 404 is returned and no participant is created

#### Scenario: Disable is idempotent

- GIVEN an already disabled link with `disabled_at = T`
- WHEN it is disabled again
- THEN HTTP 204 is returned, `disabled_at` is still `T`, and no second
  `reusable_link.disabled` audit row exists

#### Scenario: Two disables queued behind the row lock write one audit row

- GIVEN two disables of the same active link issued concurrently
- WHEN both complete
- THEN both answer 204, `disabled_at` was set once, and exactly one `reusable_link.disabled`
  audit row exists

#### Scenario: Wrong project, other organization, malformed or unknown id is 404

- GIVEN a link of project P2, a link of organization B, a malformed id and an id that does
  not exist
- WHEN each is disabled through project P of organization A
- THEN each returns HTTP 404 and no link changes

#### Scenario: Disabling works on a closed project

- GIVEN a link whose project is now `inactive`
- WHEN an admin disables it
- THEN HTTP 204 is returned

#### Scenario: No re-enable, edit, rotate or re-show operation exists

- GIVEN the registered routes
- WHEN the routes under `/api/projects/{project}/reusable-links` are listed
- THEN exactly three operations exist: create, list and disable
- AND `PUT`, `PATCH` and `GET` on a single link are not routable

#### Scenario: Participants created by the link survive

- GIVEN a link with 3 visitors
- WHEN the link is disabled
- THEN the 3 participants remain, with `reusable_interview_link_id` still set

### Requirement: Authorization Matrix For The Admin Operations

Create, list and disable MUST all require an authenticated backoffice user with
`ParticipantPolicy::create` inside `TenantContext`. The `api-m2m`, `api-candidate`, and
unauthenticated callers MUST be refused with HTTP 401 on all three; a `viewer` MUST be
refused with HTTP 403 (the authorization check runs before the project is resolved, so even a
foreign project answers 403 to a viewer); a caller reaching another organization's project or
link MUST receive 404. A superadmin with no acting organization MUST be refused with HTTP 409
on create and disable (the `org.context` rule of every organization-owned write). No
reusable-link credential (the link token) MUST authenticate any route.

| Caller | create | list | disable |
|---|---|---|---|
| admin (own org) | 201 | 200 | 204 |
| operator (own org) | 201 | 200 | 204 |
| viewer (own org) | 403 | 403 | 403 |
| admin/operator, other org's project or link | 404 | 404 | 404 |
| superadmin without an acting organization | 409 | n/a | 409 |
| M2M API key (`api-m2m`) | 401 | 401 | 401 |
| candidate JWT (`typ:candidate`, incl. a visitor's) | 401 | 401 | 401 |
| no credential | 401 | 401 | 401 |

The three routes MUST be catalogued in the authorization test matrix (catalogue, fixtures
and resources) in the same change that adds them.

#### Scenario: Viewer is denied on all three operations

- GIVEN an authenticated `viewer` of organization A and an active project of A
- WHEN create, list and disable are called
- THEN each returns HTTP 403 and no row is created or changed

#### Scenario: Cross-organization access is 404 for create, list and disable

- GIVEN an admin of organization A and a project and link of organization B
- WHEN the admin creates under, lists, and disables through B's identifiers
- THEN each returns HTTP 404 and discloses nothing about B

#### Scenario: An M2M key is refused

- GIVEN a valid `ApiClient` key with every scope
- WHEN it is presented to create, list or disable

### Requirement: Public Redemption Endpoint Contract

`POST /api/reusable-links/redeem` MUST be publicly accessible (no auth guard), MUST declare
`withoutMiddleware([TenantContext, RejectStaleCredentials])` like `/sso/exchange`, and MUST
read the token ONLY from the request BODY field `link_token`. It MUST NOT read the token from
the query string, a header, or a field named `token`: the default guard's parser chain reads a
`token` input and an array-shaped `token` once produced a 500 before the controller ran
(`embed-exchange` precedent), and a secret in a URL ends up in access logs. The field name and
a NAMED rate limit (never the numeric `throttle:x,y` form) are part of the contract. Any
`Authorization` header on the request MUST be ignored: it never authenticates and never changes
the outcome. The body MUST also carry the mandatory identity fields `display_name` and `email`
(see "Identity Fields Are Validated First And Independently Of The Token").

The framework's `TrimStrings` input middleware MUST be skipped on this route for the single
input key `link_token` only; `display_name` and `email` are trimmed like on every other
endpoint. A secret has exactly one spelling: without the skip, `<token>\n` and ` <token> `
would be trimmed into the valid token, a second spelling the strict format exists to refuse.
With the skip they are refused with the generic 404 like every other near miss.

On success the response MUST be HTTP 200 with exactly `{"access_token": "<typ:candidate
JWT>"}`, the same shape as `GET /api/sso/exchange` 200, and nothing else (no participant, link,
project or label data, and no echo of the identity).

(Previously: the body carried only `link_token`; `TrimStrings` was skipped for the whole route;
the redemption had no identity input.)

The redemption MUST execute in this order:

1. The named limiter `reusable-link-redeem` runs as route middleware, before the controller. It
   always counts the request against the per-IP bucket and, when the body token is well-formed,
   against the per-link bucket; a request over either limit is answered 429 before any database
   read.
2. Validation of the identity fields `display_name` and `email` (failure: HTTP 422, identical
   for any `link_token` value, no database read). `link_token` is never part of this
   validation.
3. The format check (failure: the generic 404, no database read).
4. A pre-read of the enabled link by `token_hash` with the tenant scope lifted (missing or
   disabled: the generic 404).
5. The rest of the work runs with the link's organization as the tenant context. The project is
   resolved without the tenant global scope, pinned to the link's `organization_id` and
   `project_id` (soft-deleted or missing: the generic 404).
6. The accessibility gates and the interviewability predicate, evaluated freshly OUTSIDE the
   row lock (failure: the generic 403).
7. Inside ONE transaction: `SELECT ... FOR UPDATE` the link by id and organization; if it was
   disabled in the meantime, the generic 404; if a participant of the same project already
   holds the normalized email (case-insensitive), HTTP 409 `{"message": "duplicate_enrolment"}`
   and a full rollback; otherwise insert the visitor (a `(project_id, email)` unique violation
   is the same 409), increment `uses_count`, set `last_used_at`, and mint the candidate JWT.
8. After the commit, dispatch `ParticipantCreated`.

(Reconciled with the implementation: the `TrimStrings` exception is registered on the input key
`link_token` for the whole application, not on the route; see "Identity Input Is Trimmed And
The Email Is Normalized".)

(Reconciled with the implementation: the original delta evaluated the project gates inside the
locked transaction. The implementation evaluates them BEFORE the lock, to keep the lock short,
and re-checks the things that can change the outcome under contention, the disabled flag and
the duplicate email, under the lock. The residual window in which a project closes between the
gates and the lock equals the one `GET /api/sso/exchange` has, and the interview start
re-checks interviewability. Tests pin the observable behaviour, not the lock order.)

### Requirement: Identity Fields Are Validated First And Independently Of The Token

The redeem body MUST be `{"link_token": <string>, "display_name": <string>, "email":
<string>}`. `display_name` and `email` are both MANDATORY. Validation of the identity fields
MUST run after the rate limiter and BEFORE any evaluation of `link_token`, so its outcome
depends only on `display_name` and `email`: the same invalid identity MUST yield the
byte-identical response whatever `link_token` is (valid, disabled, unknown, malformed, wrongly
typed, absent). Rules, identical to every other enrolment path: `display_name` is a required
string of at most 255 characters; `email` is a required, well-formed email address of at most
255 characters that is not under a reserved placeholder domain (see the reconciliation below).
Because the identity input is trimmed and empty strings become null before validation (see
"Identity Input Is Trimmed And The Email Is Normalized"), a whitespace-only value is "required"
and fails.

A failure MUST return the framework's standard HTTP 422 validation body (`message` plus
`errors` keyed ONLY by `display_name` and/or `email`). The response MUST NOT name `link_token`,
MUST NOT echo any submitted value, and MUST NOT contain any value derived from the token. A 422
MUST create no participant, MUST NOT read the link table, and MUST NOT change `uses_count` or
`last_used_at`. Validation covers ONLY the two identity fields: `link_token` is never part of a
validation rule set and is never named in an error, so a malformed token with a valid identity
still yields the generic 404 and not a 422.

(Reconciled with the implementation: the original delta did not refuse a reserved placeholder
address, and the spec index left it to design. The `email` rule list also carries
`NotPlaceholderEmail`, which refuses, with the framework's own invalid-email message, any
address under the two reserved placeholder domains, `@invalid.beai.local` and
`@purged.beai.invalid`, whatever its case or surrounding whitespace. Without it a visitor could
type an address that makes the row claim to be synthesised or purged, and an address equal to
the placeholder the retention purge derives for another participant could collide with it. The
rule is shared with the four other enrolment paths (see `participant-sso`); the error names
only `email` and discloses nothing about the reserved domains.)

### Requirement: Redemption Is Rate Limited Per IP And Per Link

The endpoint MUST be protected by the named limiter `reusable-link-redeem` with two limits
enforced on every request: 10 per minute per client IP (the address the framework resolves,
`$request->ip()`) AND 100 per hour per link, keyed by the SHA-256 of the presented well-formed
token and never by the raw token, and never by the client address. Both limits MUST be
overridable through configuration without a code change: the environment variables
`REUSABLE_LINK_REDEEM_PER_IP_PER_MINUTE` and `REUSABLE_LINK_REDEEM_PER_LINK_PER_HOUR`
(configuration `reusable_links.redeem.per_ip_per_minute` and `per_link_per_hour`, both present
in `.env.example`).

EVERY attempt MUST count against its buckets: successes, 403s, 404s, 409s and 422s alike (the
limiter runs before identity validation and never reads the identity). Counting only successes
would make the rate-limit headers differ between a valid and an unknown token, an existence
oracle. The per-link limit MUST apply identically to well-formed tokens that exist and that do
not, so a 429 discloses nothing about existence. Malformed input (not a well-formed token,
including arrays and null) counts only against the IP bucket. The limiter reads the token from
the body only, exactly like the controller. A limited request MUST return HTTP 429 with a
`Retry-After` header, MUST be evaluated before any identity validation and any database lookup
of the link, and MUST NOT create a participant or change `uses_count`.

(Previously: "successes, 403s and 404s alike"; the limiter was evaluated before the format
check only.)

Because the framework reports the TIGHTER of the two buckets in the `X-RateLimit-*` headers,
header sequences of a real and an unknown token are comparable only when each series comes from
a disjoint block of client addresses.

### Requirement: Redemption Is Atomic, Serialized And Race-Safe With Disable

The link row MUST be locked (`SELECT ... FOR UPDATE`) for the duration of the redemption
transaction, so that concurrent redemptions are serialized: N concurrent redemptions of one
link with N distinct emails MUST yield N distinct visitors and `uses_count` = N (no lost
update; the counter is derived from the locked row, never from the pre-read). The disabled flag
and the duplicate-email check MUST be evaluated under that lock. The JWT mint MUST happen
inside the transaction so that a mint failure rolls back everything (no participant,
`uses_count` unchanged, no event). A 409 MUST roll back everything in the same way.
`ParticipantCreated` MUST be dispatched only after the commit, exactly once per successful
redemption.

(Previously: "N distinct display-name numbers" was part of the serialization guarantee; the
duplicate-email check and the 409 rollback did not exist.)

A redemption racing a disable MUST either complete before it (and create its visitor) or be
refused after it (generic 404); a visitor MUST NEVER be created after the disable commits. Two
redemptions with the same email MUST create exactly one participant: through one link they are
serialized by the row lock, through different links or paths the `(project_id, email)` unique
constraint decides and the loser receives the 409.

### Requirement: A Duplicate Email In The Same Project Is Refused With 409 And Never Resumed

Inside the redemption transaction, AFTER the link row is locked and the disabled flag
re-checked, the redemption MUST check, case-insensitively, whether a participant of the SAME
project (the link's own organization and project) already holds the normalized email. If one
does, the response MUST be HTTP 409 with exactly the body `{"message": "duplicate_enrolment"}`
(the internal API's convention of a machine code in `message`, reusing the platform's published
term). A violation of the `(project_id, email)` unique constraint raised by the insert (a
concurrent enrolment through any path) MUST be mapped to the same 409. Only that constraint
maps to 409.

A 409 MUST roll the transaction back completely: no participant is created, `uses_count` and
`last_used_at` are unchanged, no `ParticipantCreated` is dispatched, no `webhook_deliveries`
row is created and no token is minted. The redemption MUST NEVER resume, re-mint a token for,
update, or take over the existing participant, whatever its status or origin (visitor of any
link, SSO-created, M2M-created, operator-created): the 409 body carries nothing about it. A 409
is reachable only after the token, project and gate checks have passed, so only a holder of a
valid, enabled link on an open project can observe it, and it can only reveal enrolment in that
one project; the same email in another project or another organization MUST NOT conflict, and
no response discloses any other tenant. A disabled link (404) and a failing gate (403) take
precedence over 409; invalid identity (422) takes precedence over everything.

### Requirement: The Raw Token And Its Hash Are Never Exposed Outside The Creation Response

The raw token MUST appear only in the single 201 creation response (inside `entry_url`).
Neither the raw token nor `token_hash` MUST appear in: any list or other admin payload; any
audit row (before, after, or metadata); any application log line or exception context; any
Sentry event (request body, query, URL, breadcrumbs, contexts, extras, messages, spans, log
records); any queued job payload or domain event; any cache key; any webhook, `/v1` or export
payload; or a model's array/JSON serialization. The 404 and validation responses MUST NOT
echo the submitted value.

The api error-report scrubber MUST filter the keys `link_token`, `token_hash` and
`token_hashes` and MUST replace every string matching `beai_rl_[A-Za-z0-9_-]{16,}` at any
depth and in every carrier, including the URL-path pass (a token pasted into a client-chosen
URL path segment is the one carrier the query and fragment cut does not reach). The
`{16,}` form is a deliberate superset of the 51-character token: it also catches a truncated
token and a token followed by more URL-safe characters, while the 16-character display prefix
alone (`beai_rl_` plus 8 characters) and a 15-character tail stay untouched. The Nuxt
applications use the same pattern (see `observability`).

(Reconciled with the implementation: any key containing the word `token` at any position is
already denied by the scrubbers' content-word rule, so a key literally named `token_prefix`
is filtered too. That is the fail-closed side. The 16-character prefix survives only as a
VALUE under a neutral key, which is what the specification means by "the prefix is not a
credential".)

## Known limitations and owner decisions

This section is non-normative. It records what the implementation deliberately does not
solve and what the owner decided, so that nobody discovers them in production.

1. **Trusted proxies (unverified in production).** The api configures no `trustProxies`
   (verified absent in `app/`, `bootstrap/` and `config/` on the implementing branch). The
   per-IP bucket is keyed on `$request->ip()`, so behind a proxy that does not forward the
   client address every visitor probably shares ONE bucket of 10 per minute; the existing
   `embed-exchange` limiter has the same latent property. The per-link bucket (100 per hour,
   keyed on the token hash) is the PRIMARY brake, and it is proven independent of the client
   address. Setting `trustProxies` to `*` without a proxy allow-list would be wrong: it would
   make `X-Forwarded-For` client-controlled and the per-IP bucket bypassable. How the deployed
   stack presents client addresses needs access to the deployment, which was neither
   authorized nor probed. A separate change for an environment-driven proxy configuration is
   recommended; until then `REUSABLE_LINK_REDEEM_PER_IP_PER_MINUTE` is the knob if a kiosk's
   shared address throttles legitimate visitors.
2. **Per-visit cost.** A leaked link can start at most 100 interviews per hour until it is
   disabled, and each completed visit costs real provider and LLM spend (visitors are LIVE).
   This is accepted; the brakes are the limiters and Disable.
3. **GDPR (closed for new visitors).** Visitors are identified by a self-declared, UNVERIFIED
   name and email entered before the interview, so an access or erasure request can be matched
   to a visitor by email. Legacy anonymous rows created before the change remain (placeholder
   email, `<label> #<n>` name); the retention sign-off (CLAUDE.md ruling 2) still names them,
   their artifacts and the link label. This is a documented default pending sign-off, not a
   legal conclusion.
4. **Webhooks and `/v1` treat visitors like any participant** (decided): the creation
   `progress` webhook, the `evaluation` webhook, `/v1/interviews` lists and exports of the live
   key include them. Integrators tell them apart by the `rlv_` `candidate_ref` prefix.
5. **Test cost.** The real-concurrency tests (separate processes against a throwaway committed
   database) take about 22 seconds and create throwaway databases named `*_conc_*`; a
   hard-killed run can leave one behind on the test server (harmless, drop it manually). The
   throttle matrix takes about 36 seconds. Run broad suites in parallel.
6. **Wording gap (closed).** The candidate app's terminal `link_invalid` state once reused a
   message that said the link "has expired or is not valid", which is slightly untrue for a
   link that never expires. The copy now says the link "is not valid or is no longer active"
   and is true for expired single-use links and for unknown or disabled reusable links;
   `interview-frontend` pins that it never claims expiry.
7. **Error-report scrubber pattern parity (closed).** The api and the two Nuxt applications now
   use the same `beai_rl_[A-Za-z0-9_-]{16,}` pattern (see `observability`); a wrapper guard that
   compares them lands with the pin bump that carries the unified patterns.
8. **Superadmin without an organization.** Create and disable answer 409 for a superadmin with
   no acting organization (the generic organization-context rule); the backoffice form shows its
   generic error banner, with no dedicated copy.
9. **Case-sensitive uniqueness residual (G-43).** `participants_project_id_email_unique` is
   case-sensitive and the admin entry link, M2M and SSO exchange store the address as received.
   The redemption pre-check is case-insensitive and stores lower case, but a race with a path
   that stores mixed case is not blocked by the index. Follow-up G-43
   (`docs/specs/public-api/DECISIONS-NEEDED.md`).
10. **Email squatting and the project-scoped enrolment oracle.** A link holder can enrol someone
    else's address (blocking that person's later invite in that project) and can test whether an
    address is enrolled in THAT one project. This is bounded by the limiter (10 per minute per
    IP, 100 per hour per link), visible to operators in the participant list with the link
    marker, and accepted (owner decision OD-1: the identity is unverified).
11. **Server access logs may carry the participants search term.** The admin participants
    search sends `q` in the query string of an authenticated GET, and an operator can search by
    an email address. The error-report scrubber is pinned for it; access logs of the hosting
    platform are outside this change. Recorded as a follow-up.
12. **A lost redemption response cannot be retried.** If a redemption succeeds on the server
    but its response never reaches the page, the visitor is enrolled without a session, and a
    Retry with the same email is refused with 409 `duplicate_enrolment` because the enrolment
    is never resumed. An idempotency key on the redemption would let a retry return the
    original result. Out of scope for this change; recorded as a follow-up (see
    `interview-frontend`, "Reusable Entry Route").
